## 打开 .sql 显示内容与实际不符（PluginText 乱码根因）
- 现象：双击 .sql（含 txt/log/md/csv/json/sql 等纯文本类）显示内容与磁盘实际存储不符（乱码）。
- 数据流核对：主程序 `on_treeView_doubleClicked`→`FileManager::QGetFileContent`（filemanager.cpp:1069）按 `nContentPositon`+`nFileLen` 读**原始字节**，字节本身正确（无越界/截断/偏移错），因此问题不在读档，在 PluginText 的显示解码。
- 根因：`Plugins/PluginText/mainwindow.cpp` 的 `showText` 用 `QString str(array)`（即 `QString::fromUtf8`）**强制按 UTF-8 解码**。`.sql` 在中文 Windows 上多存为 GBK/ANSI（Notepad ANSI、SSMS ANSI、mysqldump 到 GBK 等），按 UTF-8 解码即乱码，表现为"显示与存储不符"。
- 修复：`PluginText` 新增静态 `decodeText(const QByteArray&)`，解码顺序：① BOM 优先（EF BB BF→UTF-8 并跳 BOM；FF FE→UTF-16LE；FE FF→UTF-16BE 交换字节）；② 无 BOM 时做**严格 UTF-8 合法性校验**（自写 `isStrictUtf8`，拒绝过长短编码/超 U+10FFFF/非法续字节），通过则 UTF-8；③ 否则 `QTextCodec::codecForLocale()`（中文 Windows=GBK）兜底，`fromLocal8Bit` 再兜底。`showText` 改为 `ui->textEdit->setText(decodeText(array))`。
- 验证：Qt5.13 MinGW64 在隔离临时目录 `qmake -spec win32-g++ && mingw32-make`，5 个 .o（含 mainwindow.o、plugintext.o、两个 moc）**编译零错误**；仅最后链接成 DLL 阶段报 `undefined reference to QWidget/QObject`（沙箱手动 qmake 未挂 Qt 导入库的环境问题，非代码问题，QtCreator 可链接）。临时构建目录已清理。
- 注：此修复同时改善所有纯文本类扩展（.sql/.txt/.csv/.json 等）在 GBK/ANSI 下的显示；UTF-8 与 UTF-8+BOM 文件维持原行为。

## 打开 EPUB 失败（PluginBook 解析根因）
- 现象：双击 EPUB 报"解析电子书失败 / 未找到可显示的内容"。PluginBook.dll 已存在且依赖仅标准 Qt/MinGW DLL（objdump 确认），故非加载失败，失败在运行时 `loadEpub`。
- 根因：原 `loadEpub` 用 Qt 私有类 `QZipReader`（`QtGui/private/qzipreader_p.h`，头注释明确"非 Qt API、版本间可能变化"），其 `fileData(fileName)` 以 `QString::fromLocal8Bit(fileHeaders[i].file_name) == fileName` 做**原始条目名**精确匹配；而 `loadEpub` 的查找键会 `while(p.startsWith('/')) p.remove(0,1)` 去掉前导 `/`。真实 EPUB（多数打包工具）条目名常带前导 `/`，导致每个 `fileData()` 都返回空 → `m_entries` 全空 → 解析失败。此外 `QZipReader` 是脆弱的私有 API。
- 修复：新增自包含 `zipreader.{h,cpp}` 替代 `QZipReader`：
  - 解析 EOCD（`0x06054b50`，从尾部回溯）→ 遍历中央目录（`0x02014b50`）取条目名/压缩方式/压缩与未压缩大小/本地头偏移；按本地头跳过名+extra 后定位数据。
  - `normalize()` 统一条目名（去 `./`、去前导 `/`、反斜杠→`/`），`contains()`/`entry()` 用归一化名做匹配（大小写不敏感），**彻底免疫前导 `/`、`./`、`\` 差异**。
  - `inflate()` 用 zlib `::inflateInit2(&strm, -MAX_WBITS)`（raw deflate，EPUB 用裸 deflate 非 zlib 包裹）→ `::inflate`/`::inflateEnd` 解压（注意 `::` 前缀避免与成员函数 `ZipReader::inflate` 重名冲突）。
  - `detectFormat` 的 ZIP 块（读 `mimetype`）、`loadEpub`、`loadFb2` 的 ZIP 块均改为 `ZipReader`；不再 include `qzipreader_p.h`/`QBuffer`。`PluginBook.pro`：`QT` 去掉 `gui-private`（仅 `core gui widgets xml`），`SOURCES`/`HEADERS` 加 `zipreader.cpp/.h`，末尾 `LIBS += -lz`（链接 MinGW 自带静态 `libz.a`，无需部署 zlib1.dll）。`pluginBook.json` 描述由"基于 Qt QZipReader"改为"自包含最小 ZIP 读取器"。
- 验证：Qt5.13 MinGW64 在临时目录 `qmake -spec win32-g++ && mingw32-make`，6 个 .o（含 zipreader.o、mainwindow.o、pluginbook.o、两个 moc）**编译零错误**；仅最后链接成 DLL 阶段报 `undefined reference to QWidget/QObject`（沙箱手动 qmake 未挂 Qt 导入库的环境问题，非代码问题，QtCreator 可链接）。Grep 确认 `.cpp/.h` 已无 `QZipReader`/`qzipreader_p` 残留。
- 注：本修复同时改善 FB2（ZIP 内 XML）解析健壮性；MOBI 仍走 libmobi 不变。

## PluginPdf 构建报 `Error 1` 但程序能跑：QMAKE_POST_LINK 的 `|| true` 在 Windows 无效
- 现象：`Makefile.Debug:80: ../../FileWrapper/debug/plugins/PluginPdf.dll Error 1`，但主程序（含已部署 PluginPdf.dll）可正常运行。
- 真因：报错落在 recipe 的**第 80 行 = post-link 拷贝 `Qt5Pdfium.dll` 那一步**，而不是第 79 行的链接命令。链接其实成功（否则 DLL 不会生成、程序也跑不起来）。拷贝失败是因为目标 `Qt5Pdfium.dll` 被运行中的程序占用（共享锁，`copy /y` 无法覆盖）。而 `PluginPdf.pro:57` 与 `FileWrapper.pro:69-73` 的 `QMAKE_POST_LINK` 末尾都写了 `|| true`——`true` 在 Windows `cmd.exe` 里**不是合法命令**，拷贝一旦失败就会去执行 `true` 再次报错，整个 recipe 返回非零 → make 抛 `Error 1`。属"项目级共病"（FFMPEG 5 个 dll 拷贝同款缺陷）。
- 修复：两处 `.pro` 的 `|| true` 全部改为 `|| echo skip`（`echo` 在 cmd/sh 中均为内建且恒返回 0，可正确吞掉"尽力部署、失败跳过"的语义）。已用 qmake 重新生成 `build-…-Debug/Plugins/PluginPdf/Makefile.Debug` 验证第 80 行变为 `cp -f "..../lib/Qt5Pdfium.dll" "..../FileWrapper/debug" || echo skip`。
- 注意：修复后若程序正在运行，新 `Qt5Pdfium.dll` 仍不会被覆盖（copy 被 skip），但构建不再失败；要确保部署新版运行库需**先关闭程序再构建**。若仅改插件代码、运行库未变，则无影响。

## PluginMedia 切换文件后上一个视频仍在后台播放（QAudioOutput 不随 tab 移除而停止）
- 现象：打开视频文件正常播放，切换到其他类型文件后，上一个视频仍继续发声/解码。
- 真因：`FileWrapper/mainwindow.cpp::on_treeView_doubleClicked` 切换文件时 `removeTab(nCurIndex)` 只从 tab 移除旧 widget，**不停止其播放**；旧 `PluginMedia` widget 被隐藏但 `QAudioOutput`（音频）与 `VideoWorker` 解码线程仍在后台运行。而 `getPluginWidget()` 每个插件只返回单一 widget，所以"视频→其他类型"必然走 removeTab 路径、且没有任何停止钩子。视频→视频走同 widget 复用路径（`showVideo` 开头已 `clearFFmpegResources`），本身正常，故 bug 仅出现在跨插件类型切换。
