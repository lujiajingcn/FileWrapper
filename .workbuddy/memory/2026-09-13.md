## 多标签页增强：同类型多标签页各自独立（本次实现）
- 需求（用户选项 A）：解决旧实现「每种插件类型只有一个共享 widget → 同类型多标签页只有激活页有内容」的限制。
- 方案：给接口加**实例工厂**，主程序为每个标签页创建独占插件实例。
  1. `FileWrapper/plugininterface.h` 新增两个虚函数：
     - `virtual PluginInterface* createInstance() { return nullptr; }` —— 返回该插件的**新独立实例**；返回 nullptr 表示不支持多实例（主程序降级为共享实例，仅告警不崩溃）。
     - `virtual bool hasBackgroundPlayback() const { return false; }` —— 是否有后台播放（仅 PluginMedia 覆盖为 true）。
  2. 5 个插件各自实现 `createInstance()` → `return new PluginXxx;`（构造即建独立内部窗口，5 个插件写法一致）。
     未用 `override` 关键字以与既有代码风格一致；正确性由运行时自检保证（见下）。
  3. `FileWrapper/mainwindow.h/.cpp` 改造：
     - `TabDoc` 增加 `ownsInterface`（独占/共享）、`needsRender`（渲染缓存）；删除已无意义的 `m_pMountedWidget` 与未定义的 `initTabWidget()` 声明。
     - `resolvePlugin(...)` 签名增加 `bool &bOwned`：优先 `createInstance()` 取独占实例，失败回退共享实例并 `qWarning`。
     - `activateTab()`：**不再在标签页之间迁移 widget**（每页常驻挂载自己的窗口）；挂载时用 `QSignalBlocker` 包住 removeTab/insertTab/setCurrentIndex 防重入；仅在 `needsRender` 时渲染。
     - 新增 `destroyTabAt(index)`（先摘页再 `delete` 独占实例，最后删占位页；共享/模板窗口不删）、
       `stopCurrentPlaybackAndInvalidate()`（停播 + 若 `hasBackgroundPlayback()` 则把该实例所在页标记需要重渲染）。
     - `closeAllTabs()` / `~MainWindow()` 改为逐个 `destroyTabAt`；析构先 `disconnect(ui->tabWidget, nullptr, this, nullptr)` 防重入。
     - `onTabCloseRequested` 关闭前先 `stopPlayback()`。
     - 复用路径（同页换同类型文件）会 `delete` 掉多余的临时实例并 `setTabText` 更新标题。
- 关键机制：渲染缓存 `needsRender` 让切换标签页不再重复解析（EPUB 等大文件受益）；只有被停播的流媒体页会失效重渲染。

## 续：QtCreator 报 `[Makefile:43: sub-FileWrapper-make_first] Error 1`（两个真正的隐藏根因）
- **根因 A（Makefile 命令语法取决于"生成 qmake 的那个 shell"）** —— 这是本机最容易踩且最隐蔽的坑：
  - qmake 生成 Makefile 时，会探测 PATH 里有没有 `sh.exe`。有（Git Bash / MSYS 环境）→ 生成 **Unix 语法**：
    `DEL_FILE = rm -f`、`MKDIR = mkdir -p`、`CHK_DIR_EXISTS = test -d`、`COPY = cp -f`。
    没有（纯 Windows PATH）→ 生成 **cmd 语法**：`del`、`mkdir`、`if not exist`、`copy /y`。
  - 我此前"重跑 qmake 消除 F: 路径"时是在 **Git Bash** 里跑的 → 生成的正是 Unix 语法 Makefile；
    而 QtCreator 用 cmd.exe 驱动 make → `test -d` / `mkdir -p` / `rm -f` 全部 `is not recognized` → 在第 43 行
    `sub-FileWrapper-make_first` 处报 **Error 1**。（当时我在 Git Bash 里跑 `mingw32-make` 却能过，正是因为它有 sh。）
  - 修复：**用精简 PATH 重跑 qmake**，即把 Git Bash 的 `/usr/bin`（含 sh.exe）从 PATH 剔除，只留
    `C:\Qt\Qt5.13.0\5.13.0\mingw73_64\bin;C:\Qt\Qt5.13.0\Tools\mingw730_64\bin;C:\Windows\System32;C:\Windows`。
    所有 8 个 Makefile（顶层 + FileWrapper + Plugins + 5 插件）都要这样重生成。
  - 判定方法：`grep -m1 '^DEL_FILE' Makefile` → `del` 才对，`rm -f` 就是被 Git Bash 污染的。
- **根因 B（cmd 内置 `copy` 不认正斜杠路径）** —— 这才是 `PluginMedia.dll 找不到指定的模块` 的真正源头：
  - 实测：cmd 环境下 `copy /y "E:/a/b.dll" "E:/dst"` → 报「系统找不到指定的文件，已复制 0 个文件」；
    改成反斜杠 `copy /y "E:\a\b.dll" "E:\dst"` → 「已复制 1 个文件」。
  - 所以 `FileWrapper.pro` 的 post-link（拷 5 个 ffmpeg 运行库）与 `PluginPdf.pro` 的 post-link（拷 Qt5Pdfium.dll）
    **在 QtCreator 下从来没成功过一次**，一直被 `|| echo skip` 吞掉；缺了 avcodec/avformat/swresample/swscale，PluginMedia 自然加载失败。
  - 修复：两处都改用 `$$shell_path(...)` 把路径在 Windows 上归一化成原生反斜杠。写法：
    `FFMPEG_BIN = $$shell_path($$PWD/../../ffmpeg-.../bin)`、`FFMPEG_DST = $$shell_path($$OUT_PWD/debug)`，
    然后 `QMAKE_POST_LINK = $$QMAKE_COPY "$$shell_path($$FFMPEG_BIN/avcodec-62.dll)" "$$FFMPEG_DST" || echo skip`。
  - 另：多条 copy **不能用 `;` 串联**（`;` 是 sh 的分隔符，cmd 里不是），要用
    `$$escape_expand(\\n\\t)` 展开成 Makefile 里各自独立的一行命令，否则只有第 1 个 DLL 会被拷。
- 最终验证（本机实测，**在精简 PATH 下做**，等同 QtCreator 环境）：
  1. 8 个 Makefile 的 `DEL_FILE` 全为 `del`；`[FG]:study_lujiajing` 在 Makefile 中零残留。
  2. `mingw32-make -f Makefile`（顶层 subdirs）**TOP EXIT=0**，无 error / is not recognized。
  3. post-link 实测输出 `已复制 1 个文件。`；debug 目录下 5 个 ffmpeg DLL + Qt5Pdfium.dll 全部就位。
  4. 离屏运行：`[Plugin] Loaded` **5/5**、`Load failed` **0**、`.a` 报错 **0**。
- 排查方法论（值得复用）：**遇到 Qt/CMake 构建报错，先判定"是谁在跑 make、Makefile 用哪套 shell 语法"**，
  再判定"路径分隔符是否匹配该 shell"。这两个问题都不体现在源码里，只在生成物与执行环境里，靠读源码永远找不出来。
- `reset-qt-config.bat` 已增强：除备份 `.pro.user*` 外，还会**删除 `build-*/` 下所有 `Makefile*` 与 `.qmake.stash`**
  （保留 `.o` 以便增量），强制 QtCreator 用 cmd 语法重新生成；脚本内并注明"切勿用 Git Bash 手动跑 qmake"。

## PluginMedia「播放视频时暂停按钮失效」修复（本轮）
- 现象（用户）：播放视频文件时点暂停按钮没反应。
- **两个独立根因，必须都修**（这是本条的要点）：
  1. **主因：`.ui` 的 `<connections>` 段与 `connectSlotsByName` 重复连接 → 槽被调用两次。**
     `uic` 总会生成 `QMetaObject::connectSlotsByName(MainWindow);`（`ui_mainwindow.h` 第 177 行），
     而 `mainwindow.ui` 的 `<connections>` 段又让 uic 额外生成 6 条显式
     `QObject::connect(playPauseBtn, SIGNAL(clicked()), MainWindow, SLOT(on_playPauseBtn_clicked()))`（第 170-175 行）。
     两个机制都在同一个 `setupUi()` 里 → 点一次按钮 `on_playPauseBtn_clicked` 被调用**两次**
     → `m_bPaused = !m_bPaused` 翻转又翻回 → 暂停按钮完全失效。
     其它 5 个槽（stopBtn/progressSlider×3/volumeSlider）同样被重复连接，但它们都是幂等赋值，故没暴露。
  2. **次因（隐蔽的线程模型缺陷）：`setPaused` 用了 `Qt::QueuedConnection`。**
     `VideoWorker` 在 `m_videoThread` 里，`doDecode()` 是 QueuedConnection 进入的、且是直到播放结束才返回的
     `while(true)` 长循环 → 整段播放期间占着该线程事件循环 → 任何 QueuedConnection 的槽调用都**永远送不到**。
     文件里 `requestStop`/`clearStopRequest`/`updateGenId`/seek 的 `setPaused` **全部**用的 `DirectConnection`，
     只有播放/暂停这两处用了 QueuedConnection —— 明显是遗漏。改为 DirectConnection（`setPaused` 只做原子写 +
     条件变量唤醒且自加锁，从主线程直调线程安全）。**恢复路径也必须一起改**，否则暂停后无法唤醒。
- 修复：
  - `Plugins/PluginMedia/mainwindow.ui`：**整段删除 `<connections>`**（98 行、纯删除），改由
    `connectSlotsByName` 单一负责。前提：6 个槽全部符合 `on_<控件>_<信号>` 命名约定（已核对）。
  - `Plugins/PluginMedia/mainwindow.cpp`：`on_playPauseBtn_clicked` 里两处 `QueuedConnection` → `DirectConnection`，
    并加注释说明原因（防止后人改回去）。
  - 其余 4 个插件的 `.ui` **无** `<connections>` 段、也**无** `on_*` 槽（用手写 connect），故不受此缺陷影响。
- 验证（自建测试台 `WorkSpace_FileWrapper/_mediapause/`，TARGET `fwmedia_pause_check`）：
  加载**真实** `PluginMedia.dll` + 用 ffmpeg 生成真实 12s 测试视频（`testsrc` + sine，每帧不同），
  点击真实的 `playPauseBtn` 并观测。**关键**：不能用「暂停期间画面冻结」做判据 ——
  `onFrameDecoded`/`onAudioPtsUpdated` 在主线程用 `m_bPaused` 提前 return，
  bug 存在时同样看起来"冻结"，无法区分。真正的判据是**恢复之后是否跳变**：
  | 观测 | 修复前 | 修复后 |

  | 暂停 3 秒内进度前进 | 3120 ms | **0 ms** |
  | 恢复后增量（真实约 600ms） | — | 640 ms（无跳变） |
