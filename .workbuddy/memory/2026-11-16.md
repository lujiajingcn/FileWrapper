# 2026-11-16 合并失败「条目内容区重叠」—— 0 字节文件导致的假阳性

## 用户报告
合并 `E:\testfiles_copy` 报错：
`[FileManager] "文件合并失败：临时归档校验失败：条目内容区重叠（第 635 条与前一区间冲突）"`

## 根因（已完整确证，非猜测）
1. **写入端** `writeV2Header`（`filemanager.cpp:513`）按文件长度累加内容偏移：
   `cp += infos.at(i).nFileLen`。**0 字节文件不推进游标**，于是「它自己」和
   「它后面那条」共享同一个 `contentPos`。这在语义上**正确**（0 字节文件不占内容区）。
2. **解析端** `parseFromDevice`（`filemanager.cpp:233`）的重叠检测把**零长度区间
   `[P,P)` 也纳入判定**。排序后 `[P,P)` 与 `[P,P+N)` 首地址相同，而 `std::sort`
   **不保证稳定** → 两者相对次序未定义：
   - `[P,P)` 排在前 → `P < P` 假 → 不报错
   - `[P,P+N)` 排在前 → `P < P+N` 真 → **误报「内容区重叠」**
3. 因此**是否触发取决于排序结果**，报错位置随目录结构漂移 —— 这正是
   「第 635 条」这种位置不稳定的报错。

## 实测证据
- `E:\testfiles_copy`：9665 文件 / 4.6 GB，其中 **8 个 0 字节文件**
  → Python 独立复算 contentPos 布局：恰好 **8 对相邻条目共享 contentPos**
- 真实 `FileManager` 复现：100 文件、第 63 个为 0 字节 → 报
  `条目内容区重叠（第 64 条与前一区间冲突）`，与用户报错**同构**
- 扫描 224 种 (N, zeroAt) 组合：**22 种触发**，修复后 **fail=0**

## 修复
`FileWrapper/filemanager.cpp` 的重叠检测：**零长度条目不参与重叠判定**
（`if (e.size == 0) continue;`）。零长度条目本就不占内容区，无从重叠；
非零长度区间的真重叠仍被拦截。

## 修复后验证
| 项目 | 结果 |
|---|---|
| 真实 `E:\testfiles_copy` 合并 | **成功**：9665 文件 / 4.57 GB / 190.9 s |
| 产物大小 | 4,911,821,479 B（与 Python 独立推算 `hdrSize+总字节` **完全一致**） |
| 产物 `verifyArchive` | **9665 个文件内容 CRC32 全部匹配** |
| 产物抽检 5 条目 | 归档内内容 == 磁盘源文件 |
| 产物分割 | **成功 9665 / 失败 0**，产出 9665 文件 |
| 安全防护未削弱 | 真重叠/完全同址/越界 **仍全部被拦截**（5 场景全 PASS） |
| 修复回归 | 21 例全 PASS（新增 `mergezero` 40 断言） |

## 新增回归用例 `mergezero`（40 断言）

## 新增踩坑（12-16）
12. **沙箱会拦截子进程递归扫描 `E:\testfiles_copy`**：Bash 自身 `ls`/`find`
    正常，但 exe 里用 `QDirIterator`/`QDir::entryInfoList` 递归该目录时进程

    程序只读清单，不再自己递归。需 `dangerouslyDisableSandbox` 才会真正生效。

# 第二轮：进度对话框「正在合并:」前缀固定靠左

## 用户诉求

## 根因（实测确证，非推测）

且 label 宽度 = 文本宽度。对话框宽度在**首次 show 后固定**，但状态文本长度随
「正在合并: `<文件名>` (`<已写>`/`<总量>`)」变化 → 文本在固定宽度的 label 内居中 →
**起始位置随文本长度变化 → "正在合并:" 左右漂移**。

像素级实测（3 个不同长度的文件名）：
- 修复前：前缀起始像素 x = **0 / 144 / 0** → 漂移 **144 px**

## 修复

合并/分割/校验/导出/保存都走它）加 3 行：
```cpp
if (QLabel *pStatusLabel = dlg->findChild<QLabel*>())
    pStatusLabel->setAlignment(Qt::AlignLeft | Qt::AlignVCenter);
```

改完全局生效，且文字左边缘与下方进度条左端严格对齐。

# 修复：树形显示时双击文件夹无法展开/收起（2026-11-17）

## 现象（用户反馈）
文件列表处于「树形显示」时，双击文件夹没有展开/收起的效果。

## 根因（两个问题叠加，均已实证）

### 问题 1：首次双击未选中的行，`doubleClicked` 信号根本不会发出
`QAbstractItemView::mouseDoubleClickEvent` 要求 `pressedIndex == index`，
而 `pressedIndex` 只在「按下时该行已经是 currentIndex」时才会被置上。
→ 第一次双击一个还没选中的文件夹，只完成了「选中」，双击信号被静默丢弃。

实测（真实 MainWindow + 真实鼠标事件）：
```
TREE [mouse] dbl#1 currentBefore=(row=-1 valid=0) signalFired=0 expanded=1 currentAfter=(row=0)
TREE [mouse] dbl#2 currentBefore=(row=0  valid=1) signalFired=1 expanded=1 currentAfter=(row=0)
```
即第 1 次双击无信号，第 2 次才有。

### 问题 2：QTreeView 自带的 expandsOnDoubleClick 与业务侧 setExpanded 互相抵消
`QTreeView::expandsOnDoubleClick` 默认 true。业务侧 `setExpanded(idx, !isExpanded(idx))`
折叠之后，QTreeView 的默认逻辑又把节点展开回去，净效果 = 没变。
实测（槽内加临时探针）：
```
[DBG] dbl #1 row=0 leaf=0 expandedBefore=1
[DBG] dbl #1 -> setExpanded, expandedAfter=0     <- 槽里确实折叠了
...随后测试读回 expanded=1                        <- 被树控件翻了回去
```
→ **用户第一次双击文件夹时看到的「毫无反应」，其实是两次故障叠加**：
既没有展开，也没折叠。

## 修复（FileWrapper/mainwindow.cpp + .h）

## 踩坑
24. `openFileInCurrentTab()` 会**复用当前标签页**，标签页数量不变 ——
    判定「是否打开文件」必须看**标签页标题**（会变成文件名），不能看数量。
25. `QStandardItemModel` 的目录节点没有 `setData()`，`item->data().isValid()`
    为 false —— 这就是区分「目录节点」与「文件叶子」的可靠标志。
26. `QTreeView::expandsOnDoubleClick` 默认为 true，会和业务侧手动展开打架；
    要么关掉它，要么不要自己再 toggle 一次。
27. 想验证「鼠标双击」必须发真实鼠标事件（`QTest::mouseDClick`），
    `emit view->doubleClicked(idx)` 绕过了整条事件链，测不出这类问题。
